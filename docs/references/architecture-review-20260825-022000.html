CANDIDATE 01

The report artifact has no module

Strong

Files

  • src/cowork_agent/app.py :1213–1293
  • src/cowork_agent/features/ai_chat/controller.py :892–909, 1336–1370
  • frontend/src/dashboard/components/ArtifactsView.tsx
  • frontend/src/dashboard/components/ChatStreamView.tsx :555

Problem

Three independent pieces of code resolve data/reports for themselves, with three different parents[n] walks, and each re-decides what a safe filename is. There is no module — only a folder that four call sites agree about by coincidence.

app.py:1213 — inside create_app(), unreachable from tests
REPORTS_DIR = Path(__file__).resolve().parents[2] / "data" / "reports"
controller.py:895 — local import, inside a try/except that swallows
reports_dir = Path(__file__).resolve().parents[4] / "data" / "reports"

Two live defects fall out of the missing module

  1. The AI Chat write path does not sanitize. The three HTTP routes each guard with Path(name).name and reject "."/"..". The controller writes reports_dir / generated_report.filename where filename arrives verbatim from the model's JSON (ports.py:50 declares it as a bare str). A traversing filename escapes the folder, and the surrounding except Exception logs it at WARNING and moves on.
  2. The frontend calls two routes that do not exist. ArtifactsView.tsx builds /api/v1/reports/{f}/download and /api/v1/reports/{f}/pdf. Neither is registered anywhere in app.py or api/. Nothing catches this because no single module owns the report artifact's surface on either side of the wire.

Solution

One Report Artifact store module. It owns the folder location (injected once at the composition root, not derived from __file__), owns the filename rule, and exposes a narrow interface: save(artifact), list(), read(name), delete(name), reveal(). Sanitization becomes a ReportFilename value object that cannot be constructed from an unsafe string, so the AI Chat path gets the same guard as the HTTP path by construction rather than by remembering. The routes and the controller both become callers.

Benefits

  • Locality — "where do report artifacts live and what may they be named" becomes one answer instead of four.
  • Leverage — the missing /download and /pdf routes become two small additions on a store that already exists, rather than a fourth path walk.
  • Test surface — today the only way to test report saving from AI Chat is to drive a 617-line streaming method with a fake LLM and then look at the real repo's data/ folder. With the store injected, a traversal attempt is a three-line unit test, and the chat path can assert against an in-memory store.
  • Deletion test — passes. Deleting the store forces the sanitization rule back into four call sites — it concentrates complexity, it doesn't just relocate it.

CANDIDATE 02

The runtime is a 440-line closure and a bag of 60 attributes

Strong

Files

  • src/cowork_agent/app.py :295–733 (lifespan)
  • src/cowork_agent/api/chat.py — 11 getattr(state) reads
  • src/cowork_agent/api/projects.py — 8 getattr(state) reads
  • tests/conftest.py, tests/unit/test_chat_runtime_composition.py

Problem

Everything the application is made of — the Postgres pool, migrations, every repository, the mailbox adapters, the Email RAG providers, the AI Chat reply provider, the digest worker, the evaluation runtime — is constructed inside one lifespan closure nested in create_app(), and published by assigning app.state.<something>. There are 60 such keys. app.state is SimpleNamespace: no type, no schema, no failure when a key is missing.

The result is that every consumer defends itself. getattr(request.app.state, "x", None) appears 28× in app.py, 11× in api/chat.py, 8× in api/projects.py, alongside cast(Any, ...) to get mypy past the untyped edge. That is a shallow interface in the strict sense: the interface (a name and a hope) carries almost none of the meaning, so the meaning has to be re-stated by every caller.

Solution

Move construction out of the closure into a Runtime module — build_runtime(settings) -> CoworkRuntime, a frozen dataclass with typed fields and explicit | None where a capability is genuinely optional. create_app() keeps one line of state (app.state.runtime = await build_runtime(...)) and a runtime(request) accessor replaces every getattr/cast pair.

The existing branch structure survives intact — build_runtime still picks Postgres or SQLite off database_url(), and the lazy psycopg imports stay lazy. This is not a rewrite of what gets built; it is giving the thing that gets built a name and a type.

Benefits

  • Test surface — the seam moves from "boot a FastAPI app and hope the right attributes appeared" to "construct a CoworkRuntime with the fakes you want". Seven test files currently reach for create_app() to get at composed objects; most of them want a runtime, not an HTTP server.
  • Leverage — a missing or renamed dependency becomes a mypy error at the composition root instead of a None that travels three layers and surfaces as a 500 in production.
  • AI-navigability — "what does this app consist of" becomes one dataclass to read, instead of grepping app.state across four files.
  • Deletion test — passes. Deleting CoworkRuntime pushes 60 optional-attribute contracts back out to every caller.

Reinforces ADR-001 — which mandates ports/adapters with substitutable fakes. A typed runtime is where that ADR's intent actually gets enforced; today the adapter boundary is real but the composition edge above it is untyped.

CANDIDATE 03

Half the HTTP surface never moved to a router

Worth exploring

Files

  • src/cowork_agent/app.py :743–1560 (~30 inline routes)
  • src/cowork_agent/api/chat.py, projects.py, evaluation_jobs.py — the pattern that works

Problem

The repo already has a router convention and three modules that follow it. Everything else — Gmail and Outlook OAuth, mailbox connections, digest runs, the company knowledge endpoints, reports, and raw process documents — is defined as decorated closures inside create_app(), together with 16 module-level _helper(request) functions that exist only to serve them.

The cost is concrete, not stylistic. A closure route cannot be imported, so it cannot be unit-tested — testing any of these means constructing the whole app. And the file's own comments record the friction: RAW_DOCS_DIR carries "module-level so tests and handlers agree on one location; do not shadow them with a local copy here", while REPORTS_DIR — 30 lines later — is exactly the local copy that warning is about.

Solution

Four routers matching the boundaries that already exist in the domain: create_mailbox_router() (OAuth + connections + unread preview), create_digest_router() (runs, results, tasks), create_knowledge_router() (ready, documents, chat), create_report_router() (reports + raw documents, on the store from candidate 01). The 16 _helper(request) functions become FastAPI dependencies typed against the runtime from candidate 02.

Best done after 01 and 02: with a typed runtime, moving a route out of the closure is mechanical. Without it, each moved route drags its getattr defence along.

Benefits

  • Locality — "how does a mailbox connection work end to end" stops being a scroll through a 1,286-line function.
  • Test surface — routers can be mounted on a bare FastAPI() with a fake runtime; the current tests that reach for create_app() mostly do so to get at three routes.
  • Leverage — app.py is the single most-changed file in the repo (83 commits). Splitting it turns most of those future commits into small-file diffs and kills a standing merge-conflict hotspot across branches.
  • Caveat — this is the lowest-insight candidate: it's mostly code movement, and it earns its place through 01 and 02 rather than on its own.

CANDIDATE 04

One chat turn is one 617-line generator

Strong

Files

  • src/cowork_agent/features/ai_chat/controller.py :536–1153
  • src/cowork_agent/features/ai_chat/memory_gateway.py — private methods reached into

Problem

ChatController.stream_message is a single async generator that interleaves eight concerns line by line: idempotency and replay, cancellation, durable turn persistence, progress-activity emission, intent routing, memory and RAG context assembly, the LLM stream with its citation / title / task-proposal / report extraction, and error-code mapping. None of them is separable — they are woven, not stacked.

Two symptoms make the interleaving measurable. The cancellation check turn_id in self._cancelled_turn_ids or await is_cancelled() is written out 8 times; the pair _set_activity(...) then yield activity_event appears 7 times. Each repetition is a place a future contributor can forget one half.

The Memory gateway seam leaks too. The controller calls three underscore-private methods across the boundary — _read_project_documents, _read_active_turns, _read_task_episode. The gateway's real interface is wider than its public interface admits, which is exactly the shape that makes a fake gateway in a test diverge from the real one.

Solution

Model the turn as what it already is: a chat turn pipeline of ordered stages over one TurnState — admit (scope check, idempotency, replay) → route → assemble context → generate → extract artifacts → settle. The two cross-cutting concerns become the pipeline's job rather than each stage's: a TurnJournal that owns "set activity, persist it, emit the event" as one call, and a cancellation guard the driver checks between stages instead of eight inline conditions.

Then promote the three private gateway methods to the public interface — or fold their callers into read_context, which is what _read_project_documents looks like it wants. Either way the gateway stops having a second, undeclared interface.

Benefits

  • Test surface — today "does a degraded RAG read still emit the right warning" needs a full fake reply provider, a fake gateway, an idempotency key and a cancellation callback. Per-stage, it's one function and one input.
  • Locality — the cancellation contract and the activity contract each get one home instead of eight and seven.
  • Leverage — this is where AI Chat features land. Every future route, memory type, or artifact kind currently means another branch woven into the same 617 lines.
  • Deletion test — passes for TurnJournal and the cancellation guard. It's borderline for the stages themselves: split badly, they become six shallow modules passing a fat TurnState around. That risk is the main thing to grill.

CANDIDATE 05

Settings read the filesystem behind the caller's back

Worth exploring

Files

  • src/cowork_agent/config.py — 20 Settings classes, 37 load_env_file sites
  • integrations/llm/langfuse_bootstrap.py, last_resort.py
  • orchestration/worker.py

Problem

Every settings class exposes the same signature — from_env(environ=None, *, load_env_file=True) — and the default means that calling it with no arguments reads .env and config off disk, then falls back to os.environ. The interface looks pure; the implementation touches the filesystem. That's a hidden dependency repeated 37 times, once per class, so the escape hatch has to be remembered at every call site rather than being structural.

The failure this produces is already known in this project: a test that deletes a provider API key from the environment does not actually delete it, because the next from_env() reloads it from .env — and the test then makes a real, billed provider call instead of exercising the missing-key path. The mitigation lives in tests/conftest.py, which has to neutralize the developer's ambient POSTGRES_MODE, DATABASE_URL, cert bundle and RAG provider before anything else can run.

load_dotenv(..., override=False) is a sound choice and the comment explaining it is good. The problem isn't the policy — it's that the policy is applied lazily, 37 times, from wherever the first caller happens to be, with Path.cwd() as its root.

Solution

Resolve the environment once, at the composition root, into a frozen Environment mapping, and make every from_env take it as a required argument — GmailSettings.load(env). load_runtime_environment() becomes the one function that touches disk, called from main() / build_runtime() and from the eval CLIs. The load_env_file keyword disappears from 37 signatures, because there is nothing left for it to switch off.

A test then constructs an Environment literal. Deleting a key stays deleted.

Benefits

  • Test surface — the seam becomes an argument instead of a monkeypatch of process-global state. Several conftest guards become unnecessary rather than load-bearing.
  • Locality — one place decides what "the environment" is, including which directory .env is read from — currently Path.cwd(), which differs between the API, the worker, and an eval CLI.
  • Leverage — config.py is the second most-changed file (46 commits); each new provider currently copies the same hidden-dependency shape.
  • Cost — this is the widest-blast-radius candidate: 37 signatures and their callers. Mechanical, but not small.

CANDIDATE 06

One hook runs two different protocols

Worth exploring

Files

  • frontend/src/dashboard/hooks/useStreamingChat.ts — 1,822 lines
  • frontend/src/dashboard/hooks/useStreamingChat.test.tsx — 1,090 lines

Problem

The largest file in the repository. The hook body alone runs from line 575 to 1,822 and holds 8 useState, 12 useRef and 26 useCallback, returning a 27-member object.

Two unrelated protocols live inside it. One is the AI Chat SSE stream. The other is the digest run mail scan: when the user types @mail, the hook posts a run, then polls /v1/mail-todo/runs/{id} every 1.5s until a terminal status, aggregating progress into a synthetic assistant message. That is the Email RAG workflow — request/response polling with its own state machine — driven from inside the chat streaming hook. AGENTS.md is explicit that these are "two decoupled workflows — do not merge them"; on the client they share one hook and one message list.

Note what is already right: roughly 440 lines above the hook (citationFromEvent, activitiesFromPayload, messagesFromTurns, workflowFromTaskProposal, …) are pure wire decoders. They are good — they just aren't a module, so they're only reachable by importing the hook's file.

Solution

Three modules where there is one file. chatWire.ts — the pure decoders, lifted as-is, with their own tests. useMailScan.ts — the digest-run poller, owning its interval, abort and terminal statuses, exposing startScan(providers) → MailScanProgress. useStreamingChat.ts — session, transcript, draft and SSE only, consuming useMailScan as a collaborator.

Benefits

  • Test surface — the 1,090-line test file currently drives everything through one hook with mocked fetch. Decoder tests become plain function tests; mail-scan tests stop needing an SSE stream to exist.
  • Locality — the decoupling AGENTS.md asserts for the backend becomes visible on the client too.
  • Leverage — 26 commits in four months, and it's the file most likely to conflict when two branches touch chat.
  • Deletion test — passes for useMailScan (deleting it puts a polling state machine back into the SSE hook) and for chatWire (deleting it scatters wire-shape knowledge into components).

Considered and deliberately not proposed expand
Unifying the SQLite and Postgres repository pairs

postgres.py / sqlite_chat.py, projects.py / sqlite_projects.py and friends are ~3,000 lines of near-parallel implementation, which looks like a duplication finding. It isn't one to act on. ADR-010 decides explicitly that Postgres is the control plane and that chat memory must not be ported to SQLite to chase latency; SQLite is the absent-DATABASE_URL fallback only. Extracting a shared abstraction here would invest in parity the project has decided not to want.

Splitting domain/_chat_contracts_memory.py (1,480 lines)

Large, but it is a contracts file — mostly frozen dataclasses re-exported through chat_contracts.py. Size here isn't depth debt; splitting it would add navigation cost for no change in interface complexity.

features/batch_evaluation/ (runner 1,186 · contracts 575 · jobs repo 1,260)

Big and recently very active, but the activity is a long series of hardening commits — lease ownership, cancellation cleanup, replay bounds, watchdog progress. That reads as a module converging, not one fighting its own shape. Worth re-reviewing once it stops changing weekly.

Top recommendation

Start with 01 — the report artifact store.

It is the smallest of the six and the only one that closes live defects rather than only reducing future cost. An unsanitized, model-supplied filename is written to disk today, and the artifacts UI calls two endpoints that were never built. Both are direct consequences of the same missing module, which is the cleanest possible demonstration that the module is load-bearing.

It is also the right first move strategically. Candidates 02 and 03 are the large, valuable ones — but 03 is mostly code movement that only pays off once 02 exists, and 02 is a 60-key refactor that is much easier to justify and to review once one concrete dependency has already been threaded through a typed constructor. The report store is that first dependency: small enough to land in one pass, and it becomes the first typed field on CoworkRuntime.

Then 02, then 04. Candidate 02 unblocks 03 and makes 04's stage extraction testable. Candidate 05 is real and memory-confirmed but has the widest blast radius — worth doing deliberately, not first. Candidate 06 is independent of all of them and can run in parallel on the frontend.
