# Technical Reference: Hosting Turbovec Vector Index Snapshots on Supabase Storage

**Date**: 2026-08-13  
**Status**: Authoritative Reference Specification for Email-Agent-v1  
**Target File**: `docs/references/supabase-turbovec-snapshot-storage.md`  
**Primary Tech Stack**: Turbovec (4-bit TurboQuant Rust Index), Supabase Storage (S3-Compatible Object Store), Supabase Postgres (Metadata & RLS), Python `supabase-py` SDK

---

## 1. Executive Summary & Core Objectives

In stateless container environments (e.g., FastAPI backend instances, AWS ECS, GCP Cloud Run, or Vercel serverless workers), local disk storage is ephemeral. When process containers restart or scale horizontally, any local binary vector index snapshot (`.tvim`) generated by `TurbovecSemanticMemory` is lost.

Rebuilding a vector index from scratch on every process boot requires re-embedding all corpus text chunks via external LLM/Embedding API calls. For a corpus of 1,000 to 10,000 text chunks, this causes a **5 to 10-second startup latency penalty** and wastes embedding API credits.

### Core Objectives:
1. **Decouple Vector State from Local Disk**: Host all `.tvim` vector index snapshots on **Supabase Cloud**.
2. **Sub-50ms Cold-Start Boot**: Enable `TurbovecSemanticMemory` to download pre-computed `.tvim` binary snapshots from Supabase Storage during process initialization in **< 50 ms** (or **< 5 ms** if cached locally with matching ETag/SHA-256).
3. **Cloud-Synchronized Dynamic Updates**: Ensure dynamic updates, re-indexing, or new email ingestion automatically upload refreshed `.tvim` snapshots back to Supabase Storage with optimistic concurrency protection.

## 2. Background & Technical Context

### 2.1 Turbovec Vector Index Architecture
As detailed in recent benchmark literature (*AlphaMatch Blog 2026*, *TurboQuant ICLR 2026*):
- **TurboQuant Quantization**: Turbovec implements a data-oblivious 4-bit scalar quantization algorithm developed by Google Research and NYU. It applies random orthogonal rotations to map high-dimensional embeddings (e.g., 1024-dim Jina or 1536-dim OpenAI vectors) into uniform statistical distributions.
- **Zero Training Phase**: Unlike traditional Product Quantization (PQ) in FAISS, Turbovec requires no time-consuming $k$-means training or codebook calibration pass. Vectors can be added and serialized immediately.
- **Extreme Compression Footprint**:
  - Unquantized 32-bit Float vector ($D=1024$): $1024 \times 4\text{ bytes} = 4,096\text{ bytes} = 4.096\text{ KB}$ per vector.
  - Turbovec 4-bit Quantized vector ($D=1024$): $1024 \times 0.5\text{ bytes} = 512\text{ bytes} = 0.512\text{ KB}$ per vector (**8x memory reduction**).
  - 1,000 Chunks $\approx$ **500 KB** `.tvim` file.
  - 10,000 Chunks $\approx$ **5.1 MB** `.tvim` file.
  - 100,000 Chunks $\approx$ **51 MB** `.tvim` file.

### 2.2 Serialization Format (`.tvim`)
Turbovec exposes two primary Rust/Python serialization methods:
- `IdMapIndex.write(file_path: str)`: Atomically serializes the quantized codebook matrix, float scale vectors, feature dimension parameters, and `uint64` ID map to binary disk format.
- `IdMapIndex.load(file_path: str)`: Loads the binary memory map back into SIMD-accelerated RAM structures.

## 3. Storage Architecture: Supabase Storage vs. Postgres `bytea` / Large Objects

A critical decision is whether to store binary `.tvim` snapshots in **Supabase Storage (S3-compatible object bucket)** or directly inside PostgreSQL using the `bytea` data type or `pg_largeobject` facility.

### Comparative Assessment Matrix

| Dimension / Metric | **Supabase Storage (S3-Compatible Bucket)** | **Supabase Postgres (`bytea` / `pg_largeobject`)** | Architectural Impact & Winner |
| :--- | :--- | :--- | :--- |
| **Download Latency (Cold Start)** | **15 – 35 ms** (Direct CDN / HTTP Range / S3 stream) | **100 – 300 ms** (SQL driver parsing, binary decoding) | **Supabase Storage (~5x faster)** |
| **Database Performance & Bloat** | **Zero DB Bloat** (Files isolated in object storage) | **Severe DB Bloat** (WAL write log amplification, MVCC tuple bloat, vacuum pressure) | **Supabase Storage protects DB health** |
| **Maximum File Payload Size** | **Up to 5 GB** (TUS resumable / S3 multipart) | **1 GB column limit** (Requires complex custom byte-chunking logic) | **Supabase Storage scales without limits** |
| **Caching & Protocol Efficiency** | Native **HTTP ETag**, `If-None-Match`, `304 Not Modified`, Edge CDN | Custom SQL query required for timestamp comparison; no native HTTP edge caching | **Supabase Storage provides built-in conditional caching** |
| **Security & Access Control** | **PostgreSQL RLS** on `storage.objects` table + Private Signed URLs | PostgreSQL standard SQL RLS on custom snapshot tables | **Tie (Both leverage Postgres RLS)** |
| **Storage Infrastructure Cost** | **$0.021 / GB / month** (AWS S3 standard object storage tier) | **$0.125+ / GB / month** (High-IOPS PostgreSQL Database compute/disk) | **Supabase Storage is ~6x cheaper** |

### Architectural Decision:
Use **Supabase Storage** as the primary binary object store for `.tvim` snapshots (`turbovec-snapshots` bucket). Combine it with a lightweight **Postgres Metadata Table** (`turbovec_snapshots`) to track version tags, SHA-256 checksums, tenant scoping, and chunk counts.

## 4. Lifecycle Flow & Integration Specification for `Email-Agent-v1`

```text
  +-------------------------------------------------------------------------------+
  |                             Email-Agent-v1 Process                            |
  |                                                                               |
  |  +---------------------------+  (1) Check Cache   +------------------------+  |
  |  | TurbovecSemanticMemory    |------------------->| Local Disk Cache       |  |
  |  |                           |<-------------------| (/tmp/turbovec_cache)  |  |
  |  +---------------------------+   (Hit: < 5 ms)    +------------------------+  |
  |                |                                              ^               |
  |                | (Miss: Fetch Cloud Snapshot)                 |               |
  |                v                                              |               |
  |  +---------------------------+   (2) GET payload  +------------------------+  |
  |  | SupabaseSnapshotManager   |------------------->| Supabase Storage S3    |  |
  |  |                           |<-------------------| (turbovec-snapshots)   |  |
  |  +---------------------------+   (< 35 ms dl)     +------------------------+  |
  |                |                                                              |
  |                | (3) Query metadata / verify hash                             |
  |                v                                                              |
  |  +-------------------------------------------------------------------------+  |
  |  | Supabase Postgres DB (turbovec_snapshots table & RLS policies)          |  |
  |  +-------------------------------------------------------------------------+  |
  +-------------------------------------------------------------------------------+
```

### 4.1 Cold-Start Process Initialization (< 50 ms Target)
1. **Bootstrap Step**: `TurbovecSemanticMemory.build_index()` is called during API/Worker startup.
2. **Local Cache Check**:
   - The application checks `/tmp/turbovec_cache/snapshots/{tenant_id}.tvim`.
   - If present, it checks the local SHA-256 checksum against the active metadata row in `turbovec_snapshots` (or sends an HTTP `HEAD` request to Supabase Storage checking the `ETag`).
   - **Cache Hit**: Loads index into RAM via `IdMapIndex.load()` in **< 5 ms** with **0 API calls**.
3. **Cloud Snapshot Download (Cache Miss / New Container)**:
   - Issues a fast stream download via `supabase.storage.from("turbovec-snapshots").download("snapshots/{tenant_id}/latest.tvim")`.
   - Payload download of a ~500 KB to 5 MB file finishes in **15–35 ms**.
   - Writes payload atomically to `/tmp/turbovec_cache/snapshots/{tenant_id}.tvim`.
   - Calls `IdMapIndex.load()` to initialize vector search in RAM. Total time elapsed: **< 50 ms**.
4. **Fallback Handling**:
   - If no snapshot exists in Supabase Storage (e.g., new tenant onboarding), the system falls back to building the index in memory from text chunks, writing the local `.tvim` file, and uploading the initial snapshot back to Supabase Storage.

### 4.2 Dynamic Updates & Re-Indexing Sync Flow
When new emails arrive or vector documents are re-indexed:
1. Ingest new text chunks and compute dense vectors via `EmbeddingPort`.
2. Apply unit normalization and zero-pad feature dimension to a multiple of 8 (`_pad_vector_dim`).
3. Update or rebuild the in-memory Turbovec index (`self._index.add_with_ids(...)`).
4. Write updated snapshot to local disk (`self._index.write(tmp_path)`).
5. Compute SHA-256 hash and byte length of the updated file.
6. Upload the file to Supabase Storage using `upsert="true"`:
   - Target path: `snapshots/{tenant_id}/latest.tvim`.
   - Optional versioned path: `snapshots/{tenant_id}/v_{timestamp}_{sha256[:8]}.tvim`.
7. Upsert metadata row in Supabase Postgres `turbovec_snapshots` table inside a SQL transaction.

## 5. Security, Row Level Security (RLS) & Schema Design

### 5.1 Supabase Storage Bucket Setup
- **Bucket Name**: `turbovec-snapshots`
- **Public Visibility**: `False` (Private bucket; inaccessible without proper auth tokens or service keys).

### 5.2 Storage Row Level Security (RLS) Policies
Apply fine-grained PostgreSQL policies on `storage.objects` to enforce tenant isolation:

```sql
-- Enable Row Level Security on Storage
ALTER TABLE storage.objects ENABLE ROW LEVEL SECURITY;

-- 1. Read Policy: Users can only download snapshot files within their own tenant folder
CREATE POLICY "Tenant read access to turbovec snapshots"
ON storage.objects FOR SELECT
TO authenticated, service_role
USING (
    bucket_id = 'turbovec-snapshots' 
    AND (
        auth.role() = 'service_role' 
        OR (storage.foldername(name))[2] = auth.uid()::text
    )
);

-- 2. Write/Upload Policy: Service role or tenant owner can update snapshots
CREATE POLICY "Tenant write access to turbovec snapshots"
ON storage.objects FOR INSERT
TO authenticated, service_role
WITH CHECK (
    bucket_id = 'turbovec-snapshots' 
    AND (
        auth.role() = 'service_role' 
        OR (storage.foldername(name))[2] = auth.uid()::text
    )
);
```

### 5.3 PostgreSQL Metadata Schema (`turbovec_snapshots`)

```sql
CREATE TABLE IF NOT EXISTS public.turbovec_snapshots (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id TEXT NOT NULL,
    version_tag TEXT NOT NULL,
    storage_path TEXT NOT NULL,
    file_size_bytes BIGINT NOT NULL,
    chunk_count INTEGER NOT NULL,
    sha256_checksum TEXT NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_tenant_version UNIQUE (tenant_id, version_tag)
);

CREATE INDEX IF NOT EXISTS idx_turbovec_snapshots_tenant_active 
ON public.turbovec_snapshots (tenant_id, is_active, updated_at DESC);
```

## 6. Concrete Python Blueprint Implementations

### Blueprint 6.1: `SupabaseSnapshotManager`

```python
"""Adapter for persisting and fetching Turbovec .tvim snapshots via Supabase Storage."""

import hashlib
import logging
from pathlib import Path
from typing import Optional

from supabase import Client

logger = logging.getLogger(__name__)


class SupabaseSnapshotManager:
    """Manages cloud persistence of Turbovec .tvim snapshots via Supabase Storage."""

    def __init__(self, supabase_client: Client, bucket_name: str = "turbovec-snapshots") -> None:
        self._client = supabase_client
        self._bucket = bucket_name

    def download_snapshot(
        self, tenant_id: str, destination_path: Path, expected_sha256: Optional[str] = None
    ) -> bool:
        """Downloads .tvim snapshot from Supabase Storage if missing or hash differs."""
        remote_path = f"snapshots/{tenant_id}/latest.tvim"

        # Check local file matching hash first
        if destination_path.exists() and expected_sha256:
            local_hash = hashlib.sha256(destination_path.read_bytes()).hexdigest()
            if local_hash == expected_sha256:
                logger.info("Local snapshot hash matches cloud metadata (%s); bypassing download.", expected_sha256[:8])
                return True

        try:
            payload: bytes = self._client.storage.from_(self._bucket).download(remote_path)
            downloaded_hash = hashlib.sha256(payload).hexdigest()

            # Atomic write to temporary file then replace
            destination_path.parent.mkdir(parents=True, exist_ok=True)
            tmp_path = destination_path.with_suffix(".tmp")
            tmp_path.write_bytes(payload)
            tmp_path.replace(destination_path)

            logger.info(
                "Downloaded cloud Turbovec snapshot for tenant %s (%d bytes, SHA256: %s)",
                tenant_id,
                len(payload),
                downloaded_hash[:8],
            )
            return True
        except Exception as exc:
            logger.warning("Failed to download Turbovec snapshot from Supabase Storage: %s", exc)
            return False

    def upload_snapshot(self, tenant_id: str, source_path: Path) -> Optional[str]:
        """Uploads updated .tvim snapshot to Supabase Storage with upsert."""
        if not source_path.exists():
            raise FileNotFoundError(f"Snapshot file not found at {source_path}")

        remote_path = f"snapshots/{tenant_id}/latest.tvim"
        file_bytes = source_path.read_bytes()
        sha256_hash = hashlib.sha256(file_bytes).hexdigest()

        try:
            self._client.storage.from_(self._bucket).upload(
                path=remote_path,
                file=file_bytes,
                file_options={"content-type": "application/octet-stream", "upsert": "true"},
            )
            logger.info("Uploaded Turbovec snapshot for tenant %s (SHA256: %s)", tenant_id, sha256_hash[:8])
            return sha256_hash
        except Exception as exc:
            logger.error("Failed to upload Turbovec snapshot to Supabase Storage: %s", exc)
            raise
```
