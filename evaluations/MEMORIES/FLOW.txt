-------------------------------------------------------------------------------
 1. WHAT QUESTION DOES THIS ANSWER?
-------------------------------------------------------------------------------

  NOT this:   "Can memory leak, or be written without authorization?"
              ~80 policy unit tests already answer that. They are strict.

  THIS:       "Does memory make the answer better,
               and WHICH of the four scopes actually did it?"

  The second half - WHICH scope - is the entire reason this harness exists.
  Without it you get one number ("memory helped") that nobody can check.


-------------------------------------------------------------------------------
 2. THE FOUR MEMORY SCOPES
-------------------------------------------------------------------------------

  All four are called "memory" but they behave nothing alike.

  SCOPE        WHAT IT HOLDS                     LIVES IN        LASTS
  ---------    -----------------------------     -----------     ----------
  short_term   last 20 turns of THIS chat        in-process      30 min idle
  long_term    4 profile fields:                 Postgres        90 days
               language, timezone,
               persona, tone
  episodic     tasks the user asked for          Postgres        90 days
               AND then approved
  semantic     company policy documents (vi)     RAG corpus      corpus life

  Three facts that shape everything downstream:

    * No model can write to long_term or episodic. Both need an explicit
      authorization step. So we cannot seed them by chatting at them.

    * A brand-new episode is NOT retrievable. It becomes readable only after
      an approval. Seeding episodic takes 3 steps; the others take 1.

    * semantic is OFF by default, and even when on, the question must contain
      a cue phrase or the read never fires.


-------------------------------------------------------------------------------
 3. THE CORE TRICK: ASK THE SAME QUESTION THREE TIMES
-------------------------------------------------------------------------------

  A PROBE = one question
          + what a correct answer looks like
          + EXACTLY ONE target scope

  That single declared target is what makes attribution possible.
  Each probe is asked 3 times. Only ONE thing changes between them.


    +----------------------+----------------------+----------------------+
    |        ARM 1         |        ARM 2         |        ARM 3         |
    |        "full"        |      "ablated"       |      "control"       |
    +----------------------+----------------------+----------------------+
    | memory seeded  YES   | memory seeded  YES   | memory seeded   NO   |
    | target scope    ON   | target scope   OFF   | target scope    ON   |
    | other scopes    ON   | other scopes    ON   | other scopes    ON   |
    +----------------------+----------------------+----------------------+
    | the product as it    | was the target scope | did this question    |
    | actually ships       | load-bearing?        | need memory at all?  |
    +----------------------+----------------------+----------------------+
    |  should PASS         |  should FAIL         |  should FAIL         |
    +----------------------+----------------------+----------------------+

  If the answer only changes when the target scope is removed,
  the change can ONLY have come from that scope. That is the attribution.


  !! THE ONE THING EVERYBODY GETS BACKWARDS !!
  ---------------------------------------------
  "control" turns off the SEED, not the READS.
  All four scopes stay switched ON in control - they are simply EMPTY.

  Why it matters: if control disabled the reads instead, it would just be a
  second ablation arm. A question the model can answer from training data
  would then PASS under "full" and look like a memory success.

  A PASS under control means one thing only:
  --> this probe never needed memory. It is measuring the model, not us.


-------------------------------------------------------------------------------
 4. WHAT ONE RUN ACTUALLY DOES
-------------------------------------------------------------------------------

   START
     |
     v
  [1] MAKE A THROWAWAY IDENTITY
     |    hash(probe set + model + seed) -> tenant_id / user_id
     |    PREVENTS: colliding with another run, or touching a real user
     v
  [2] FOR EACH PROBE, FOR EACH OF THE 3 ARMS ------------------------+
     |                                                               |
     |   [2a] SEED THE MEMORY   (skipped entirely for "control")      |
     |        short_term -> speak each line as a real chat turn       |
     |        long_term  -> one profile write w/ explicit provenance  |
     |        episodic   -> ask for the task, THEN approve it         |
     |        semantic   -> index a small policy corpus               |
     |        RULE: seed the way a real user would. Never write rows  |
     |              straight into the DB.                             |
     |                                                               |
     |   [2b] VERIFY THE SEED LANDED                                  |
     |        read every scope back, confirm non-empty                |
     |        PREVENTS: a failed seed reading as amnesia              |
     |                                                               |
     |   [2c] OPEN A FRESH SESSION                                    |
     |        ...unless the probe targets short_term                  |
     |        PREVENTS: the answer sitting in the prompt already,     |
     |                  so the scope under test is never consulted    |
     |                                                               |
     |   [2d] ASK THE QUESTION through the real ChatController        |
     |        collect the reply text + latency                        |
     |                                                               |
     |   [2e] SCORE THE REPLY -> PASS / MISS / STALE / INVENTED       |
     |        pure function: no model, no DB, no clock                |
     |        if the grade rests on the refusal word-list, mark it    |
     |        UNCERTAIN and count it. A human reads those, not a      |
     |        judge model - see section 5.                            |
     |                                                               |
     +---------------------------------------------------------------+
     |
     v
  [3] COLLAPSE 3 OUTCOMES -> 1 VERDICT     (the line a human reads)
     |
     v
  [4] WRITE 2 FILES
     |    baselines/<stamp>.json   committed, METADATA ONLY
     |    runs/<stamp>-detail.json gitignored, full replies for debugging
     v
  [5] TEAR DOWN
     |    delete every store this run created. Company RAG never touched.
     v
   END


-------------------------------------------------------------------------------
 5. SCORING: FOUR GRADES, NOT PASS/FAIL
-------------------------------------------------------------------------------

  PASS       the expected answer is there
             (or the probe wanted a refusal, and got one)

  MISS       the answer is simply absent.  A gap. Unhelpful but honest.

  STALE      a SUPERSEDED value was given INSTEAD of the current one.
             The user was told something false, not nothing.

  INVENTED   the probe expected a refusal and got a confident answer.
             THE HEADLINE FAILURE.

  Why four and not two:

      A system that says "I don't know" is behaving correctly under
      uncertainty. A system that confidently returns last month's answer,
      or invents one, is dangerous - and both look identical to "fail"
      on a boolean.

  One ordering rule that matters:
    STALE only fires when the expected answer is MISSING.
    "Wednesday - it moved from Tuesday" is a GOOD reply, not a stale one.

  WHAT THE SCORER WILL NOT CLAIM
  ------------------------------
  PASS / MISS / STALE are decided by looking for text the probe DECLARED.
  Those are certain by construction.

  Deciding whether a reply DECLINED is different: it rests on a list of
  refusal phrases, and that list can never be complete. So those rows are
  marked UNCERTAIN and counted in the report as `needs_reading`.

  The harness does not guess and does not ask a judge model. It says
  "I am not sure about these N rows" and the replies are waiting in runs/
  for a person to read. A benchmark may not publish a verdict it cannot
  defend - so it publishes the doubt instead.


-------------------------------------------------------------------------------
 6. VERDICTS: THE LINE YOU ACTUALLY READ
-------------------------------------------------------------------------------

  Three outcomes per probe collapse into one verdict.
  Sorted WORST FIRST, so the interesting rows are never buried.

    full      ablated   control     VERDICT              MEANS
    -------   -------   -------     -----------------    -------------------
    any INVENTED or STALE anywhere  dangerous            overrides everything
    not PASS     -      not PASS    broken               scope not delivering
    any        any      PASS        leaked               not a memory probe
    PASS      PASS      not PASS    scope_did_nothing    right answer,
                                                         wrong attribution
    PASS    not PASS    not PASS    scope_earned_it      the scope did its job

  "leaked" = the control arm passed = the question never needed memory.
  Those probes are excluded from scoring and named in the report.

 7. WORKED EXAMPLE - ONE PROBE, START TO FINISH
-------------------------------------------------------------------------------

  PROBE  st_update_01   targets: short_term   test: update
         seeded turns:  "Han chot cua viec do la thu Ba."
                        "Dinh chinh: han chot da doi sang thu Tu."
         question:      "Han chot cua yeu cau gia han CCCD la khi nao?"
         expect_any:    thu Tu
         stale_any:     thu Ba

  ARM 1  full             -> "Thu Tu - da doi tu thu Ba."           PASS
                             (thu Tu present, so stale check never runs)

  ARM 2  ablated          -> "Toi khong co thong tin ve han chot."  MISS

  ARM 3  control          -> "Toi khong co thong tin do."           MISS

         (The probe set itself is written with full Vietnamese diacritics;
          they are stripped here only because this file is plain ASCII.)

  VERDICT:  scope_earned_it
            Short-term memory did its job - and we know it was SHORT-TERM
            specifically, because it was the only thing that moved.

  WHAT EACH ARM RULED OUT:
    control said "thu Tu"           -> model guessed. Not a memory probe.
    ablated said "thu Tu"           -> something ELSE supplied it.
                                       Probe is mis-targeted.
    full said "thu Ba"              -> STALE. Correction stored but lost.
                                       Worse than forgetting.

 8. THE 8 PROBES THAT SHIP TODAY
-------------------------------------------------------------------------------

  ID                 SCOPE        TEST        CORRECT BEHAVIOUR
  ---------------    ----------   ---------   ---------------------------------
  st_recall_01       short_term   recall      says "Da Nang"
  st_update_01       short_term   update      says thu Tu, not thu Ba
  lt_recall_01       long_term    recall      names the stored timezone
  lt_restraint_01    long_term    restraint   DECLINES - no job title was set
  ep_recall_01       episodic     recall      names the CCCD renewal task
  ep_restraint_01    episodic     restraint   DECLINES - no case number exists
  sem_recall_01      semantic     recall      answers from the policy corpus
  sem_restraint_01   semantic     restraint   DECLINES - no sabbatical doc

  The shape is deliberate: every scope gets ONE recall probe and ONE
  restraint probe - can it remember, and does it stay quiet when it should.
  short_term gets the only `update` probe, because a single session is the
  only place a value can be superseded and re-asked in one run.

  There is NO isolation probe. See section 11.

  Note the wording is deliberate: both episodic probes contain "tac vu
  truoc" and both semantic probes contain "chinh sach cong ty". Those are
  RETRIEVAL CUES. No cue -> the read never fires -> the probe measures
  nothing while appearing to work.

  The cues are Vietnamese because the assistant answers only in Vietnamese.
  They were English until the cue lists were translated, which meant a
  Vietnamese question fired no retrieval at all - four of these eight probes
  silently measured nothing. A unit test now holds the probe set to it:
  tests/unit/features/ai_chat/memory_eval/test_probe_set_fires_retrieval.py

  8 probes x 3 arms = 24 model calls per full live run.

 9. TWO TIERS - WHAT GATES CI AND WHAT DOES NOT
-------------------------------------------------------------------------------

  OFFLINE TIER                          LIVE TIER
  scoring, masking, verdicts, report    real model + real Postgres + real RAG
  pure functions                        27 real model calls
  no model, no DB, no network           needs 3 external dependencies
  ---------------------------------     ---------------------------------
  RUNS IN CI: yes                       RUNS IN CI: no
  GATES: YES, must pass 100%            GATES: no - it MEASURES

  Why the live tier does not gate: small-model behaviour drifts. A hard
  assertion would make releases hostage to provider drift. A regression here
  is read by a human, not enforced by a robot.

  COMMANDS
    # mechanics only - no key, no DB, scripted replies. Measures NOTHING.
    python scripts/evaluate_memory.py --dry-run

    # real run - needs a store, a key for --provider, and an embedding key
    # (GEMINI_API_KEY, or JINA_API_KEY when DOCUMENT_EMBEDDING_PROVIDER=jina)
    python scripts/evaluate_memory.py

  EXIT CODES
    0  the run completed and a report was written
    1  no usable model - no reply to score, so there is no run
    2  the probe set could not be loaded

  !! EXIT CODE 0 DOES NOT MEAN MEMORY IS GOOD. It means the harness ran. !!

  RUN FOR REAL
    [x] against a throwaway local PostgreSQL, Vietnamese probe set.
        That first run is now a HISTORICAL RESULT, not the current state.
        It found four separate faults, three of which were in the harness
        or the questions rather than in memory:

        A. THE GRADER counted an empty reply as a memory that forgot.
           Three of twenty-four answers were empty because the provider
           was briefly unreachable, and they produced a leaked, a
           scope_did_nothing and a broken that were conclusions about an
           outage. Empty is now `NO_ANSWER` / `unreadable` - not a grade,
           and it outranks everything (SPEC 6.2, 7).
        B. TWO QUESTIONS WERE GUESSABLE. lt_recall_01 asked for a timezone
           an assistant that answers in Vietnamese will name anyway;
           sem_recall_01 accepted the ordinary Vietnamese words for
           `approve` and `manager`. Both now ask for a fact only the
           memory holds (SPEC 7.4).
        C. THE MASK WAS CHECKED BEFORE BLAMING THE QUESTIONS. One arm now
           runs end to end and asserts the hidden profile appears
           nowhere in the payload the provider is sent. If that had failed, every conclusion in
           every report so far would have been void.
        D. THE EPISODIC LOOKUP COULD NEVER MATCH. It ANDed every word of
           the user message, question frame included, against the search
           index. Nothing scored above zero, so the 0.6 threshold was
           never even reached. The query is now built from the content
           words only, ORed - the right episode scores 0.8529 where it
           scored 0.0000 (SPEC 7.5). This one WAS a product defect.

        A, B and C are why the old numbers cannot be read as findings
        about memory. D is why they should not be read as findings about
        episodic memory either.

    [ ] a fresh run on the fixed harness. NOTE that nothing in the report
        records the change: run_key hashes (probe_set_id, model, seed) and
        the questions are in none of those, and probe_set_id is still
        v1_four_scopes. So the old and new reports LOOK comparable and are
        not. See SPEC 15.1 item 8.
    [ ] repeated runs, so the variation can be reported (SPEC 7.3)
        -> until then, ONE RUN IS ONE SAMPLE. Do not compare two runs
           and call the difference a finding.

 11. WHAT THIS DOES NOT TELL YOU
-------------------------------------------------------------------------------

  Four things this harness does NOT cover. The spec's section 15 is the single
  authoritative list with the full reasoning; these are the one-line versions,
  and the first one you must know before reading any live report.

  NO ISOLATION PROBE - cross-tenant leakage is NOT measured here.
      Seeding a second tenant is not wired. A probe asking for material
      nobody seeded gets a refusal from an EMPTY STORE - it would read as a
      passing tenancy check while proving nothing in either direction.
      So it is not shipped.
      Isolation IS covered, strictly and offline, by the memory-policy
      unit tests. See SPEC 5.2 for why it may also never target semantic:
      the company RAG corpus has no tenant field anywhere, by design.

  THE LIVE TIER HAS NEVER EXECUTED END TO END.
      Expect the first real run to surface episodic seeding: an episode is
      written only when the reply provider ALSO returns a task proposal.
      Asking for a task is necessary but not sufficient. seed_episodic
      reports that as a finding rather than letting it look like amnesia.

  EPISODIC MEANS TASK EPISODES ONLY.
      write_chat_summary has no production caller, so ChatSummaryEpisode is
      reachable in tests and unreachable in the product. Do not assume
      summary episodes are covered.

  THE LAUNCH GATE IS NOT FED BY THIS.
      evaluate_launch_gate still uses its hardcoded stand-in scorer.
      Bridging real outcomes into it needs a defensible outcome-to-score
      mapping first - a decision, not a wiring task.
